# OGRE-Next Usage Guide

## Overview

**OGRE-Next** (Object-Oriented Graphics Rendering Engine Next) is a high-performance, scene-oriented 3D rendering engine written in C++. It is the successor to OGRE 1.x, completely redesigned for modern graphics APIs and hardware capabilities.

This guide is aligned with the **OGRE-Next 2.3** documentation set and the official `Samples/2.0/Tutorials/EmptyProject` scaffold. One quirk of the upstream docs is that some 2.3 pages still contain older "2.1" wording; the APIs and project layout guidance referenced here are still the relevant ones for the 2.3 manual tree.

This version of the guide is intentionally scoped to **Linux desktop rendering only**, using **OpenGL 3+ with GLX**. OGRE-Next supports other render systems and platforms, but this document treats Vulkan, D3D11, Metal, mobile targets, and headless modes as out of scope unless briefly noted for context.

### Key Features

- **High Performance**: Designed for minimal CPU overhead with approaches like AZDO (Approaching Zero Driver Overhead)
- **Modern Rendering**: PBS (Physically Based Shading), HDR, Global Illumination
- **Target Runtime**: Linux desktop with OpenGL 3.3+ via GLX
- **Advanced Material System**: HLMS (High Level Material System) for efficient shader generation
- **Compositor System**: Powerful node-based rendering pipeline configuration

## Architecture Overview

OGRE-Next follows a modular architecture with these core components:

```
┌─────────────────────────────────────────────────────────────────┐
│                        Application                              │
├─────────────────────────────────────────────────────────────────┤
│  Root │ SceneManager │ RenderWindow │ CompositorManager2        │
├─────────────────────────────────────────────────────────────────┤
│       HLMS (PBS, Unlit)  │  Compositor Nodes/Workspaces         │
├─────────────────────────────────────────────────────────────────┤
│               RenderSystem (GL3+ via GLX on Linux)              │
└─────────────────────────────────────────────────────────────────┘
```

### Core Classes

| Class | Purpose |
|-------|---------|
| `Root` | Main entry point, manages plugins and render systems |
| `SceneManager` | Manages scene graph, cameras, lights, and culling |
| `RenderWindow` | Represents the rendering output target |
| `CompositorManager2` | Manages the rendering pipeline via Compositor nodes |
| `HlmsManager` | Manages HLMS implementations (PBS, Unlit) |
| `Item` | Modern replacement for Entity (v2 object) |
| `SceneNode` | Holds transform data (position, rotation, scale) |

## Project Structure Best Practices

### Recommended Directory Layout

```
MyOgreProject/
├── build/                     # CMake build directory
├── bin/
│   ├── Debug/                 # Executables, plugins.cfg, copied runtime libs
│   ├── Release/
│   └── Data/
│       ├── Hlms/
│       │   ├── Common/
│       │   ├── Pbs/
│       │   └── Unlit/
│       ├── resources2.cfg     # Generated by the EmptyProject scripts
│       ├── Materials/
│       ├── Meshes/
│       ├── Textures/
│       └── Compositors/
├── CMake/
│   ├── Bootstrap.cmake
│   ├── Dependencies/
│   └── Templates/
├── Dependencies/
│   └── Ogre/                  # OGRE-Next source tree or symlink
├── include/
└── src/
```

The official recommendation in the manual is to start from `Samples/2.0/Tutorials/EmptyProject` rather than inventing your own layout from scratch. That scaffold already knows how to:

1. Copy the required HLMS data into `bin/Data/Hlms`
2. Generate `resources2.cfg` from a template
3. Generate `plugins.cfg` with the correct render systems for the current platform and build type
4. Copy or link the OGRE runtime libraries into the per-config `bin/<Config>` directory

One naming wrinkle worth calling out early: some older manual prose and some generic install scripts still talk about `Resource.cfg` or `resources.cfg`, but the current 2.3 `EmptyProject` and `Samples/2.0/Common` framework code use `resources2.cfg`.

For desktop builds, a good default working directory is usually `bin/Debug` or `bin/Release`, because the generated plugin and resource config files are expected relative to the executable.

### Essential Data Files

OGRE-Next requires HLMS shader template files to function, and the directory structure matters:

1. **Common/** - Shared HLMS utilities
2. **Pbs/** - Physically Based Shading templates
3. **Unlit/** - Basic unlit material templates

These are typically copied from `Samples/Media/Hlms/` in the OGRE-Next repository.

Best practices from the official docs:

1. Do **not** flatten the HLMS folders; keep `Common`, `Pbs`, and `Unlit` in their original hierarchy
2. Register HLMS before calling `ResourceGroupManager::initialiseAllResourceGroups`
3. Also bundle `Samples/Media/2.0/scripts/materials/Common` if you rely on the stock low-level/common material scripts
4. Keep optional debug assets such as `Samples/Media/packs/DebugPack.zip` nearby during development for fonts and simple debug meshes

### EmptyProject Walkthrough

The official `Samples/2.0/Tutorials/EmptyProject` scaffold is meant to get you from source checkout to first frame with as little manual setup as possible.

**What CMake generates or copies for you**

1. `bin/Data/Hlms/Common`, `bin/Data/Hlms/Pbs`, and `bin/Data/Hlms/Unlit` copied from the OGRE repository
2. `bin/Data/resources2.cfg` generated from `CMake/Templates/Resources.cfg.in`
3. `bin/Debug/plugins_d.cfg` or `bin/Release/plugins.cfg` generated from `CMake/Templates/Plugins.cfg.in`
4. `bin/<Config>/Plugins/` created on platforms where the runtime plugin layout expects a plugin subdirectory
5. Runtime libraries copied or symlinked into `bin/<Config>` when the scaffold can find them
6. `include/OgreCommon/` and `src/OgreCommon/` copied from `Samples/2.0/Common/` so you can own the app framework code instead of depending on a black-box helper lib

The `setupOgre(...)` helper that does this is part of the copied EmptyProject CMake scaffolding, not a general OGRE package API. If you later switch to an installed-package workflow, expect that part of your build setup to change.

**Typical run flow**

1. Copy `Samples/2.0/Tutorials/EmptyProject` into your own project folder
2. Put OGRE at `Dependencies/Ogre` or symlink it there
3. Configure CMake with a matching OGRE build tree
4. On Linux, adjust `CMAKE_BUILD_TYPE` and `OGRE_BINARIES` if the scaffold assumes a build type you did not produce
5. Build the project into `build/`
6. Run from `bin/Debug` or `bin/Release` so the generated plugin and resource config files are where the executable expects them
7. Extend `setupResources()` in your graphics system to add your own material/script folders after the base `resources2.cfg` has been parsed

**What the starter app does at runtime**

1. Uses a platform-specific `mResourcePath` such as `../Data/` on Linux desktop builds
2. Reads `resources2.cfg`
3. Parses regular resource sections from `resources2.cfg`, but intentionally skips the `Hlms` section during generic resource registration
4. Uses the `Hlms` section's `DoNotUseAsResource` entry to discover the root HLMS media path and register HLMS using `HlmsUnlit::getDefaultPaths()` / `HlmsPbs::getDefaultPaths()`
5. Adds extra project-specific resource folders such as `2.0/scripts/materials/PbsMaterials`
6. Stores `ogre.cfg` and `Ogre.log` in a writable per-user location when possible instead of assuming the current directory is writable

### Linux-Only `plugins.cfg`

Because this guide targets **Linux + GL3+ + GLX only**, keep the render-system setup minimal. You do not need Vulkan, D3D11, Metal, or multi-backend fallback logic in `plugins.cfg`.

**Simple Linux desktop plugin config**

```ini
Plugin=RenderSystem_GL3Plus
```

In practice, if you start from `EmptyProject`, the simplest approach is to keep the generated `plugins.cfg` / `plugins_d.cfg` but trim the template to the GL3+ plugin only. `PluginOptional` is useful for mixed-backend distributions; it is not necessary when you have already chosen a single Linux desktop render path.

### Custom `resources2.cfg` Example

If you want the EmptyProject template to know about your own assets up front, the cleanest place to do it is `CMake/Templates/Resources.cfg.in`, which is what the scaffold uses to generate `bin/Data/resources2.cfg`.

**Minimal template extension**

```ini
[Hlms]
DoNotUseAsResource=@OGRE_MEDIA_DIR@Hlms/

[General]
FileSystem=@OGRE_MEDIA_DIR@Materials
FileSystem=@OGRE_MEDIA_DIR@Meshes
FileSystem=@OGRE_MEDIA_DIR@Textures
FileSystem=@OGRE_MEDIA_DIR@Scripts

[Popular]
FileSystem=@OGRE_MEDIA_DIR@packs
```

That keeps the generated config responsible for broad, static resource roots, while your graphics-system code can still add feature-specific folders later.

**Typical code-side extension**

```cpp
void MyGraphicsSystem::setupResources()
{
    GraphicsSystem::setupResources();

    Ogre::ConfigFile cf;
    cf.load( mResourcePath + "resources2.cfg" );

    Ogre::String originalDataFolder = cf.getSetting( "DoNotUseAsResource", "Hlms", "" );

    if( originalDataFolder.empty() )
        originalDataFolder = "./";
    else if( *( originalDataFolder.end() - 1 ) != '/' )
        originalDataFolder += "/";

    const char *c_locations[] = {
        "2.0/scripts/materials/PbsMaterials",
        "2.0/scripts/materials/MyProject",
        "2.0/scripts/materials/MyProject/GLSL"
    };

    for( size_t i = 0; i < sizeof( c_locations ) / sizeof( c_locations[0] ); ++i )
    {
        Ogre::String dataFolder = originalDataFolder + c_locations[i];
        addResourceLocation( dataFolder, getMediaReadArchiveType(), "General" );
    }
}
```

Practical rule: put stable, project-wide roots in `Resources.cfg.in`, and keep per-feature or per-sample additions in `setupResources()`.

## Initialization Pattern

### Basic Application Bootstrap

For a real project, the docs recommend starting from the EmptyProject or sample framework. If you wire Ogre directly, keep your code aligned with the scaffold's loading order and `resources2.cfg` conventions. The sample below is intentionally closer to the 2.3 framework pattern than to the older "hardcode `../Data/Hlms/Common/GLSL`" tutorials.

One more nuance: the published 2.3 API docs show `Root( pluginFile, configFile, logFile, appName )`, while some upstream sample-framework code also uses Root overloads that include an `AbiCookie`. If you are following the source tree verbatim, match the constructor used by the framework code you copied; the 2.3 change that matters for app code is that the app name is now an explicit constructor parameter in the documented API.

```cpp
#include <OgreArchiveManager.h>
#include <OgreConfigFile.h>
#include <OgreRoot.h>
#include <OgreSceneManager.h>
#include <OgreRenderSystem.h>
#include <OgreRenderWindow.h>
#include <Compositor/OgreCompositorManager2.h>
#include <OgreCamera.h>
#include <OgreHlmsManager.h>
#include <OgreHlmsPbs.h>
#include <OgreHlmsUnlit.h>
#include <OgreItem.h>
#include <OgreLight.h>
#include <OgreResourceGroupManager.h>
#include <OgreWindowEventUtilities.h>

class MyApplication {
public:
    Ogre::Root* mRoot = nullptr;
    Ogre::RenderWindow* mWindow = nullptr;
    Ogre::SceneManager* mSceneManager = nullptr;
    Ogre::Camera* mCamera = nullptr;
    Ogre::CompositorWorkspace* mWorkspace = nullptr;
    Ogre::String mResourcePath = "../Data/";

    void initialize() {
        // 1. Create Root
        mRoot = OGRE_NEW Ogre::Root("plugins.cfg", "ogre.cfg", "Ogre.log",
                                    "My OGRE Application");

        // 2. Setup RenderSystem
        if (!mRoot->restoreConfig()) {
            if (!mRoot->showConfigDialog()) {
                return; // User cancelled
            }
        }

        // 3. Initialize Root (creates RenderWindow)
        mWindow = mRoot->initialise(true, "My OGRE Application");

        // 4. Create SceneManager
        const size_t numThreads = 1;
        mSceneManager = mRoot->createSceneManager(
            Ogre::ST_GENERIC, numThreads, "MainSceneManager");

        // 5. Register non-HLMS resource locations.
        setupResources();

        // 6. Register HLMS, parse scripts, and initialize resource groups.
        loadResources();

        // 7. Create Camera
        mCamera = mSceneManager->createCamera("MainCamera");
        mCamera->setPosition(Ogre::Vector3(0, 5, 15));
        mCamera->lookAt(Ogre::Vector3(0, 0, 0));
        mCamera->setNearClipDistance(0.1f);
        mCamera->setFarClipDistance(1000.0f);
        mCamera->setAutoAspectRatio(true);

        // 8. Setup Compositor (REQUIRED in OGRE-Next)
        setupCompositor();

        // 9. Create scene content
        createScene();
    }

    void registerHlms() {
        Ogre::ConfigFile cfg;
        cfg.load( mResourcePath + "resources2.cfg" );

        Ogre::String rootHlmsFolder = mResourcePath + cfg.getSetting( "DoNotUseAsResource", "Hlms", "" );
        if( rootHlmsFolder.empty() )
            rootHlmsFolder = "./";
        else if( *( rootHlmsFolder.end() - 1 ) != '/' )
            rootHlmsFolder += "/";

        Ogre::ArchiveManager &archiveManager = Ogre::ArchiveManager::getSingleton();
        const Ogre::String archiveType = "FileSystem";

        Ogre::String mainFolderPath;
        Ogre::StringVector libraryFoldersPaths;

        Ogre::HlmsUnlit::getDefaultPaths( mainFolderPath, libraryFoldersPaths );
        Ogre::Archive *archiveUnlit = archiveManager.load( rootHlmsFolder + mainFolderPath,
                                                           archiveType, true );
        Ogre::ArchiveVec archiveUnlitLibraries;
        for( const Ogre::String &libraryPath : libraryFoldersPaths )
        {
            archiveUnlitLibraries.push_back(
                archiveManager.load( rootHlmsFolder + libraryPath, archiveType, true ) );
        }
        Ogre::HlmsUnlit *hlmsUnlit = OGRE_NEW Ogre::HlmsUnlit( archiveUnlit, &archiveUnlitLibraries );
        mRoot->getHlmsManager()->registerHlms( hlmsUnlit );

        Ogre::HlmsPbs::getDefaultPaths( mainFolderPath, libraryFoldersPaths );
        Ogre::Archive *archivePbs = archiveManager.load( rootHlmsFolder + mainFolderPath,
                                                         archiveType, true );
        Ogre::ArchiveVec archivePbsLibraries;
        for( const Ogre::String &libraryPath : libraryFoldersPaths )
        {
            archivePbsLibraries.push_back(
                archiveManager.load( rootHlmsFolder + libraryPath, archiveType, true ) );
        }
        Ogre::HlmsPbs *hlmsPbs = OGRE_NEW Ogre::HlmsPbs( archivePbs, &archivePbsLibraries );
        mRoot->getHlmsManager()->registerHlms( hlmsPbs );
    }

    void setupResources() {
        Ogre::ConfigFile cfg;
        cfg.load( mResourcePath + "resources2.cfg" );

        Ogre::ConfigFile::SectionIterator sectionIt = cfg.getSectionIterator();
        while (sectionIt.hasMoreElements()) {
            const Ogre::String& sectionName = sectionIt.peekNextKey();
            Ogre::ConfigFile::SettingsMultiMap* settings = sectionIt.getNext();

            if( sectionName == "Hlms" ) {
                continue;
            }

            for (const auto& setting : *settings) {
                Ogre::ResourceGroupManager::getSingleton().addResourceLocation(
                    setting.second,
                    setting.first,
                    sectionName);
            }
        }
    }

    void loadResources() {
        registerHlms();
        Ogre::ResourceGroupManager::getSingleton().initialiseAllResourceGroups( true );
    }

    void setupCompositor() {
        // Option 1: Basic workspace helper (simplest)
        Ogre::CompositorManager2* compositorMgr = mRoot->getCompositorManager2();
        const Ogre::String workspaceName("MainWorkspace");
        
        if (!compositorMgr->hasWorkspaceDefinition(workspaceName)) {
            compositorMgr->createBasicWorkspaceDef(
                workspaceName, 
                Ogre::ColourValue(0.2f, 0.4f, 0.6f)  // Background color
            );
        }
        
        mWorkspace = compositorMgr->addWorkspace(
            mSceneManager,
            mWindow,
            mCamera,
            workspaceName,
            true  // enabled
        );
    }

    void createScene() {
        // Create a light
        Ogre::Light* light = mSceneManager->createLight();
        Ogre::SceneNode* lightNode = mSceneManager->getRootSceneNode()
            ->createChildSceneNode();
        lightNode->attachObject(light);
        lightNode->setPosition(10, 10, 10);
        lightNode->setDirection(Ogre::Vector3(-1, -1, -1).normalisedCopy());
        light->setPowerScale(Ogre::Math::PI); // For LDR pipeline
        light->setType(Ogre::Light::LT_DIRECTIONAL);

        // Create an Item (v2 object). For new projects, prefer Items over v1::Entity.
        Ogre::Item* item = mSceneManager->createItem(
            "myMesh.mesh",
            Ogre::ResourceGroupManager::AUTODETECT_RESOURCE_GROUP_NAME,
            Ogre::SCENE_DYNAMIC);
        Ogre::SceneNode* node = mSceneManager->getRootSceneNode()
            ->createChildSceneNode();
        node->attachObject(item);
        node->setPosition(0, 0, 0);
    }

    void mainLoop() {
        while (!mWindow->isClosed()) {
            Ogre::WindowEventUtilities::messagePump();
            
            if (mWindow->isVisible()) {
                mRoot->renderOneFrame();
            }
        }
    }

    void shutdown() {
        OGRE_DELETE mRoot;
        mRoot = nullptr;
    }
};
```

If you inherit from the copied `Samples/2.0/Common` framework instead of wiring this yourself, keep its `loadResources()` behavior intact. That framework also loads blue-noise and LTC matrix textures for PBS features after resource-group initialization, which is easy to omit accidentally in a hand-rolled bootstrap.

## The Compositor System

The Compositor is **essential** in OGRE-Next. Unlike OGRE 1.x, you cannot render without it.

### Compositor Concepts

| Concept | Description |
|---------|-------------|
| **Node** | Defines render targets, passes, and I/O channels |
| **Workspace** | Connects nodes together and specifies the final output |
| **Pass** | Individual rendering operation (clear, render_scene, quad, etc.) |
| **Channel** | Connection between node outputs and inputs |

### Basic Compositor Script

```
// File: MyWorkspace.compositor

compositor_node MainRenderNode
{
    in 0 rt_renderwindow
    
    target rt_renderwindow
    {
        // Clear the render target
        pass clear
        {
            colour_value 0.2 0.4 0.6 1.0
        }
        
        // Render the scene
        pass render_scene
        {
            rq_first    0
            rq_last     max
            
            // Optional: Enable shadows
            // shadows MyShadowNode
        }
    }
}

workspace MainWorkspace
{
    connect_output MainRenderNode 0
}
```

### Pass Types

| Pass Type | Purpose |
|-----------|---------|
| `clear` | Clears render target (color, depth, stencil) |
| `render_scene` | Renders scene objects |
| `render_quad` | Renders fullscreen quad (post-processing) |
| `compute` | Executes compute shaders |
| `generate_mipmaps` | Generates texture mipmaps |
| `shadows` | Batch updates shadow nodes |
| `stencil` | Configures stencil state |

## HLMS (High Level Material System)

HLMS replaces the old Material system for efficient, shader-based rendering.

Low-level `.material` / `.program` workflows are still supported and remain useful for post-processing, compositor passes, and quick shader iteration. For a new 2.3 scene-material pipeline, though, treat HLMS datablocks as the default path and keep direct `Material` / `Pass` manipulation as the exception.

### HLMS Implementations

| Implementation | Use Case |
|----------------|----------|
| **PBS** | Physically Based Shading - most materials |
| **Unlit** | No lighting - GUI, particles, billboards |
| **PBS Mobile / Unlit Mobile** | GLES2-era mobile targets |
| **Custom** | User-defined implementations |

### Creating a PBS Datablock

```cpp
Ogre::HlmsPbs* hlmsPbs = static_cast<Ogre::HlmsPbs*>(
    mRoot->getHlmsManager()->getHlms(Ogre::HLMS_PBS));

Ogre::HlmsPbsDatablock* datablock = static_cast<Ogre::HlmsPbsDatablock*>(
    hlmsPbs->createDatablock(
        "MyMaterial",               // Unique name
        "MyMaterial",               // Human-readable name
        Ogre::HlmsMacroblock(),     // Depth, culling settings
        Ogre::HlmsBlendblock(),     // Alpha blending settings
        Ogre::HlmsParamVec()        // Additional parameters
    )
);

// Set material properties
datablock->setDiffuse(Ogre::Vector3(0.8f, 0.2f, 0.2f));  // Red-ish
datablock->setRoughness(0.4f);
datablock->setFresnel(Ogre::Vector3(0.04f), false);      // Non-metallic

// Load and set textures
Ogre::HlmsTextureManager* textureMgr = hlmsPbs->getHlmsManager()->getTextureManager();
Ogre::HlmsTextureManager::TextureLocation texLoc = 
    textureMgr->createOrRetrieveTexture("diffuse.png", 
        Ogre::HlmsTextureManager::TEXTURE_TYPE_DIFFUSE);

datablock->setTexture(Ogre::PBSM_DIFFUSE, texLoc.texture, texLoc.samplerblock);

// Assign to an Item
item->setDatablock(datablock);
```

### Material Blocks

| Block | Purpose |
|-------|---------|
| **Macroblock** | Depth check/write, culling mode, polygon mode |
| **Blendblock** | Alpha blending operations |
| **Samplerblock** | Texture filtering, addressing modes |

## Scene Management

### Names Are Optional (2.0+ Change)

In OGRE-Next, names no longer need to be unique and are optional. To identify uniqueness, use `IdObject::getId()`:

```cpp
// Old OGRE 1.x style (WILL NOT WORK as expected):
// sceneManager->createEntity("myEntityName", "meshName.mesh");

// New OGRE-Next style:
Ogre::v1::Entity* entity = mSceneManager->createEntity("meshName.mesh");
entity->setName("myEntityName");  // Optional

// For uniqueness, use IDs instead of names:
Ogre::IdType uniqueId = entity->getId();
```

Note that different object types can share the same ID (e.g., an Entity and a SceneNode), but two MovableObjects will never share the same ID.

### Attachment and Visibility

In OGRE-Next, objects are always "in the scene". SceneNodes hold position information, can be animated, and can inherit transforms. Key differences from OGRE 1.x:

- **Detached objects hide themselves**: When a MovableObject is detached from a SceneNode, `setVisible(false)` is implicitly called
- **Previous visibility lost**: When attaching/detaching, the previous value of `getVisible()` is lost
- **Illegal while detached**: Calling `setVisible(true)` while detached will crash (debug assertion exists)

**Use hiding instead of detaching**:
```cpp
// PREFERRED: Hide the object (fast)
item->setVisible(false);

// AVOID: Detaching/destroying for temporary hiding (expensive)
// node->detachObject(item);  // More expensive, use only when necessary
```

### Static vs Dynamic Objects

OGRE-Next distinguishes between static and dynamic objects for performance. Static objects skip per-frame transform and AABB updates, which significantly reduces CPU load.

```cpp
// Dynamic object (default) - updates every frame
Ogre::SceneNode* dynamicNode = mSceneManager->getRootSceneNode()
    ->createChildSceneNode(Ogre::SCENE_DYNAMIC);

// Static object - rarely moves, better performance
Ogre::SceneNode* staticNode = mSceneManager->getRootSceneNode()
    ->createChildSceneNode(Ogre::SCENE_STATIC);

// After modifying a static object, notify the scene manager
staticNode->setPosition(10, 0, 0);
mSceneManager->notifyStaticDirty(staticNode);
```

**Important rules for static objects:**

1. **Static nodes** won't update derived transforms every frame - changes require `notifyStaticDirty()`
2. **Static children of dynamic parents**: Modifying the dynamic parent won't update the static child automatically
3. **Static children of static parents**: Notifying the parent automatically updates children
4. **Dynamic child of static parent**: Valid and encouraged (e.g., moving pendulum on static clock)
5. **Static child of dynamic parent**: Usually a bug unless the parent is root
6. **Static entities can only attach to static nodes**, and vice versa
7. **Calling `setStatic(true)`** automatically calls `notifyStaticDirty()` for you
8. **Batch your static updates**: Changing one static object can cause many others to update - do it all in one frame (e.g., at startup)

### Items vs Entities

| v2 Objects (Preferred) | v1 Objects (Legacy) |
|------------------------|---------------------|
| `Item` | `v1::Entity` |
| Lower memory footprint | Higher memory footprint |
| Better batching | Limited batching |
| Use `createItem()` | Use `v1::Entity` |

```cpp
// Preferred: v2 Item
Ogre::Item* item = mSceneManager->createItem("mesh.mesh");

// Legacy: v1 Entity (still supported but slower)
Ogre::v1::Entity* entity = mSceneManager->createEntity("mesh.mesh");
```

### Lights

All lights require attachment to a SceneNode (unlike OGRE 1.x where lights could be node-less):

```cpp
Ogre::Light* light = mSceneManager->createLight();
Ogre::SceneNode* lightNode = mSceneManager->getRootSceneNode()
    ->createChildSceneNode();
lightNode->attachObject(light);

// Light types
light->setType(Ogre::Light::LT_DIRECTIONAL);
light->setType(Ogre::Light::LT_POINT);
light->setType(Ogre::Light::LT_SPOTLIGHT);

// Direction is set via the node (Light::setDirection redirects to node)
lightNode->setDirection(Ogre::Vector3(0, -1, 0));

// Power scale (PI for LDR, real-world lux for HDR)
light->setPowerScale(Ogre::Math::PI);
```

**Note:** `Light::getDirection()` and `Light::setDirection()` will fail if the light isn't attached to a SceneNode. Cameras are an exception - they have their own position/rotation for simplicity and are attached to the root scene node by default.

### Obtaining Derived Transforms

OGRE-Next removed per-node dirty flags for performance. Derived transforms are only valid after `SceneManager::updateAllTransforms()` (which happens inside `updateSceneGraph()`).

```cpp
// WRONG - will trigger assert in debug mode:
sceneNode->setPosition(1, 1, 1);
Ogre::Vector3 derivedPos = sceneNode->_getDerivedPosition();  // Stale!

// CORRECT - use the "Updated" variants when you need immediate results:
sceneNode->setPosition(1, 1, 1);
Ogre::Vector3 derivedPos = sceneNode->_getDerivedPositionUpdated();

// After one Updated call, non-Updated variants are valid until next change:
Ogre::Quaternion derivedRot = sceneNode->_getDerivedOrientation();  // Now OK
Ogre::Vector3 derivedScale = sceneNode->_getDerivedScale();         // Now OK
```

**Key points:**
- `_getDerivedPosition/Orientation/Scale()` use cached values - fast but may be stale
- `_getDerivedPositionUpdated()` etc. force a transform chain update - slower but always current
- The same applies to `MovableObject::getWorldAabb()` vs `getWorldAabbUpdated()`
- Prefer doing your work after `updateSceneGraph()` has run rather than calling many `*Updated()` functions

## Main Loop Patterns

### Variable Framerate (Basic)

```cpp
void mainLoop() {
    Ogre::Timer timer;
    while (!mQuit) {
        float timeSinceLast = timer.getMicroseconds() / 1000000.0f;
        timer.reset();
        
        update(timeSinceLast);
        
        mRoot->renderOneFrame();
    }
}
```

### Deterministic Loop (Recommended for Games)

```cpp
const float FIXED_TIMESTEP = 1.0f / 60.0f;  // 60 Hz logic
float accumulator = 0.0f;

void mainLoop() {
    Ogre::Timer timer;
    while (!mQuit) {
        float frameTime = timer.getMicroseconds() / 1000000.0f;
        timer.reset();
        
        accumulator += frameTime;
        
        // Fixed timestep logic updates
        while (accumulator >= FIXED_TIMESTEP) {
            updateLogic(FIXED_TIMESTEP);
            accumulator -= FIXED_TIMESTEP;
        }
        
        // Interpolate for smooth rendering
        float alpha = accumulator / FIXED_TIMESTEP;
        interpolate(alpha);
        
        mRoot->renderOneFrame();
    }
}
```

## Threading

OGRE-Next uses a **synchronous threading model**. When multithreading is enabled, all worker threads are woken and complete their work before the main thread continues. This provides determinism and simplifies reasoning about thread safety.

### Thread Count Recommendations

```cpp
// SceneManager creation with threading
const unsigned int hwThreads = std::thread::hardware_concurrency();
const size_t numThreads = hwThreads > 1u ? static_cast<size_t>( hwThreads - 1u ) : 1u;

mSceneManager = mRoot->createSceneManager(
    Ogre::ST_GENERIC, numThreads, "MainSceneManager");
```

**Ideal thread count:**
- Treat `std::thread::hardware_concurrency()` as a hint, not a guarantee; it may return `0`
- Start from the number of worker threads your machine can actually spare after your own game logic, physics, audio, networking, and tooling threads are accounted for
- The 2.3 API docs explicitly say not to oversubscribe the system; the practical rule is "total busy threads should fit the machine"
- Example: if the machine can keep 4 cores busy and your app already needs 1 fully busy core, give Ogre about 3 worker threads
- **Don't oversubscribe**: More threads than cores just adds overhead

### Threaded Operations

OGRE-Next parallelizes these operations:
1. **Frustum culling** - determines which objects are visible
2. **Node transform updates** - calculates world positions
3. **AABB bounds updates** - calculates world bounding boxes
4. **LOD calculations** - determines appropriate detail level

### Thread Safety Rules

1. **SceneNodes can be safely modified** from any thread during `updateSceneGraph()`
2. **Don't create/destroy** objects while worker threads are active
3. **Use `SCENE_STATIC`** for objects modified from other threads - ensures no race with OGRE's internal updates
4. **InstancingThreadedCullingMethod**: Choose appropriate culling strategy based on your object count and distribution

### Instancing Thread Culling Methods

```cpp
// For scenes with few but expensive instances
mSceneManager->setInstancingThreadedCullingMethod(
    Ogre::INSTANCING_CULLING_SINGLETHREAD);

// For scenes with many instances
mSceneManager->setInstancingThreadedCullingMethod(
    Ogre::INSTANCING_CULLING_THREADED);
```

## Performance Best Practices

### DO

1. **Use LIFO creation/destruction order**: Create objects in order A→B→C, destroy in order C→B→A. This keeps memory contiguous and improves cache performance.

2. **Use SCENE_STATIC for stationary objects**: Eliminates per-frame transform and AABB updates.

3. **Use Instancing for repeated objects**: Batches similar objects together, reducing draw calls.

4. **Hide objects with `setVisible(false)`**: Much faster than detaching/destroying and recreating.

5. **Minimize bone count**: Skeletal animation performance scales with bone count.

6. **Batch static object changes**: If you must modify static objects, do them all in the same frame.

7. **Use appropriate shadow map resolution**: Balance quality vs performance based on target hardware.

8. **Profile with OGRE's built-in stats**: Use `RenderSystem::getMetrics()` and overlay stats.

### DON'T

1. **Don't update SCENE_STATIC objects frequently**: Each update can cascade to many dependent objects.

2. **Don't oversubscribe threads**: More threads than CPU cores just adds context-switch overhead.

3. **Don't call `*Updated()` functions excessively**: If you need many derived transforms, wait for `updateSceneGraph()` instead.

4. **Don't use mismatched render queue ranges**: Ensure shadow node render queues match your render_scene pass ranges.

5. **Don't detach/attach for visibility**: Use `setVisible()` instead - it's orders of magnitude faster.

6. **Don't ignore gamma correction**: PBS materials look wrong without it.

7. **Don't flatten HLMS directories**: Keep Common, Pbs, Unlit in their original hierarchy.

### Gamma Correction (Critical for PBS)

PBS (Physically Based Shading) **requires** gamma correction to look correct:

```cpp
// Method 1: Via config dialog
mRoot->getRenderSystem()->setConfigOption("sRGB Gamma Conversion", "Yes");
mRoot->initialise(true);

// Method 2: Via render window parameters
Ogre::NameValuePairList params;
params["gamma"] = "true";
mWindow = mRoot->createRenderWindow(title, w, h, false, &params);
```

**Without gamma correction:**
- Scene looks too dark or dull
- Material colors appear washed out
- Lighting calculations are mathematically incorrect

**PBS Material Calibration:**
- Use real-world color values (paper is NOT RGB 1,1,1 - it's more like 0.8)
- High Fresnel coefficients reduce diffuse contribution
- Roughness directly affects brightness
- For LDR pipelines, set light power to `Ogre::Math::PI`
- For HDR pipelines, use real-world lux values (sun ~100,000 lux)

## Custom Renderables

For advanced users creating custom MovableObject implementations:

### OGRE-Next Requirements (Changed from 1.x)

1. **Renderables must have a MovableObject**: `RenderQueue::addRenderable()` requires both a MovableObject and Renderable pointer
2. **Visitor pattern removed**: Don't implement `visitRenderables()` - populate `MovableObject::mRenderables` vector instead
3. **Multiple Renderables can share one MovableObject**: Implementations don't need to derive from both classes

```cpp
class MyMovableObject : public Ogre::MovableObject {
public:
    MyMovableObject(Ogre::IdType id, Ogre::ObjectMemoryManager* memMgr,
                    Ogre::SceneManager* mgr, Ogre::uint8 renderQueueId)
        : MovableObject(id, memMgr, mgr, renderQueueId)
    {
        // Populate mRenderables for the SceneManager to access
        mRenderables.push_back(&mMyRenderable);
    }
    
private:
    MyRenderable mMyRenderable;
};
```

## Shadow Mapping

### Shadow Node Definition

```
compositor_node_shadow MyShadowNode
{
    technique pssm
    
    texture atlas 2048 2048 PF_D32_FLOAT
    
    num_splits      3
    pssm_lambda     0.95
    
    shadow_map 0 atlas uv 0.0 0.0 0.5 0.5 light 0 split 0
    shadow_map 1 atlas uv 0.5 0.0 0.5 0.5 light 0 split 1
    shadow_map 2 atlas uv 0.0 0.5 0.5 0.5 light 0 split 2
    
    target atlas
    {
        pass clear
        {
            colour_value 1 1 1 1
        }
    }
    
    shadow_map_target_type directional
    {
        shadow_map 0 1 2
        {
            pass render_scene
            {
            }
        }
    }
}
```

### Using Shadows in render_scene

```
pass render_scene
{
    shadows MyShadowNode
    // or 'shadows MyShadowNode reuse' to reuse from previous pass
}
```

### Shadow Bias Configuration (2.3+)

OGRE-Next 2.3 replaced `HlmsManager::setShadowMappingUseBackFaces()` with **Normal Offset Bias**, a more robust technique from 2011 that drastically improves shadow quality and reduces self-occlusion artifacts.

**Shadow node bias settings:**

```
compositor_node_shadow MyShadowNode
{
    technique pssm
    
    // Control shadow bias per cascade
    constant_bias_scale 1.0      // Global constant bias multiplier
    normal_offset_bias  0.05     // Normal-based offset to reduce acne
    
    // ... rest of shadow node definition
}
```

**Key points:**
- `normal_offset_bias`: Offsets geometry along surface normals during shadow casting
- `constant_bias_scale`: Scales the constant depth bias
- These can be controlled via `ShadowTextureDefinition::normalOffsetBias` and `ShadowTextureDefinition::constantBiasScale` in C++
- Users porting from 2.2.x may need to adjust these values if shadows appear different

## Common Pitfalls & Solutions

### 1. "Scene is black/nothing renders"

**Cause**: No Compositor workspace set up.

**Solution**: Always create a workspace:
```cpp
compositorMgr->createBasicWorkspaceDef(workspaceName, bgColor);
compositorMgr->addWorkspace(sceneMgr, window, camera, workspaceName, true);
```

### 2. "Scene looks too dark"

**Causes**:
- Gamma correction not enabled
- Light power too low for PBS

**Solutions**:
```cpp
// Enable gamma correction
params["gamma"] = "true";
mWindow = mRoot->createRenderWindow(title, w, h, false, &params);

// Set light power (PI for LDR)
light->setPowerScale(Ogre::Math::PI);
```

### 3. "HLMS not found" / Shader compilation errors

**Cause**: HLMS data files not found, or HLMS was registered after resource groups were initialized.

**Solution**: Ensure HLMS shader templates are accessible, and register HLMS before initializing resource groups:
```cpp
Ogre::ConfigFile cf;
cf.load( mResourcePath + "resources2.cfg" );

Ogre::String rootHlmsFolder = mResourcePath +
    cf.getSetting( "DoNotUseAsResource", "Hlms", "" );

// Register HLMS before this call:
Ogre::ResourceGroupManager::getSingleton().initialiseAllResourceGroups();
```

For 2.3 projects, prefer the `DoNotUseAsResource` + `HlmsUnlit::getDefaultPaths()` / `HlmsPbs::getDefaultPaths()` pattern from EmptyProject over hardcoding backend folders such as `Hlms/Common/GLSL`.

### 4. "Transform not updating"

**Cause**: Using SCENE_STATIC without notifying dirty.

**Solution**:
```cpp
staticNode->setPosition(newPos);
mSceneManager->notifyStaticDirty(staticNode);
```

### 5. "Memory/Performance issues with many lights"

**Solution**: Use Forward+ (Forward3D/ForwardClustered):
```cpp
mSceneManager->setForwardClustered(true, 16, 8, 24, 96, 0, 0, 2, 50);
```

## Linux Containers and GLX Passthrough

This guide targets a **visible Linux desktop window** from a Linux host or Linux devcontainer using **OpenGL 3+ with GLX**. Headless EGL and Vulkan null-window workflows are deliberately out of scope for the main path described here.

### Ogre-Side Choices

For this container workflow, keep the Ogre build aligned with the desktop path:

1. Enable `OGRE_BUILD_RENDERSYSTEM_GL3PLUS`
2. Enable `OGRE_GLSUPPORT_USE_GLX`
3. Keep `OGRE_CONFIG_UNIX_NO_X11` disabled

That means the container is expected to talk to an X11 server on the host, usually directly on X11 or through XWayland on Wayland desktops.

### Required Host-to-Container Passthroughs

To open a visible OGRE window from a Linux container, you typically need all of the following:

1. `DISPLAY` exported into the container
2. The X11 socket mounted, usually `/tmp/.X11-unix`
3. Permission for the container user to connect to the host X server
4. GPU device access such as `/dev/dri` for Mesa, Intel, and AMD
5. A writable home or config location if Ogre needs to write `ogre.cfg` or `Ogre.log`

For NVIDIA, GPU access is usually handled with `nvidia-container-toolkit` and `--gpus all` rather than a plain `/dev/dri` pass-through.

### Minimal `docker run` Example

On the host, allow your local user to connect to X11:

```bash
xhost +si:localuser:$(id -un)
```

Then start the container with X11 and GPU access:

```bash
docker run --rm \
    -e DISPLAY="$DISPLAY" \
    -v /tmp/.X11-unix:/tmp/.X11-unix \
    --device /dev/dri \
    my-ogre-image
```

For NVIDIA hosts, the equivalent usually looks like:

```bash
docker run --rm \
    --gpus all \
    -e DISPLAY="$DISPLAY" \
    -v /tmp/.X11-unix:/tmp/.X11-unix \
    my-ogre-image
```

### Minimal Devcontainer `runArgs`

If you are using VS Code devcontainers on Linux, the same passthrough idea usually becomes:

```json
"runArgs": [
    "-e", "DISPLAY=${localEnv:DISPLAY}",
    "-v", "/tmp/.X11-unix:/tmp/.X11-unix",
    "--device=/dev/dri"
]
```

You still need to grant X11 access on the host. Matching the container user to your host UID also reduces friction with X11 permissions and with files written into the workspace.

### Practical Notes

1. This is a **Linux-only** GUI workflow. It is not meant to be portable to macOS or Windows hosts.
2. If your desktop uses Wayland, XWayland is usually the lowest-friction way to keep GLX-based container apps working.
3. If you later need CI or offscreen rendering, add a separate headless configuration then rather than complicating the main desktop setup now.

## Memory Architecture (Advanced)

OGRE-Next uses a Structure of Arrays (SoA) memory layout for performance. Understanding this helps with debugging and custom development.

### SoA vs AoS

Traditional engines use Array of Structures:
```cpp
// AoS - Array of Structures (traditional)
struct Node { Vector3 pos; Quaternion rot; Vector3 scale; };
Node nodes[100];
```

OGRE-Next uses Structure of Arrays:
```cpp
// SoA - Structure of Arrays (OGRE-Next)
struct NodeData {
    Vector3* positions;      // All X,Y,Z packed for SIMD
    Quaternion* rotations;
    Vector3* scales;
};
```

### SIMD Packing

In SSE2 builds, `ARRAY_PACKED_REALS = 4`, meaning 4 vectors are packed together:

| Memory Layout | Content |
|--------------|---------|
| `m_chunkBase[0]` | { D.x, C.x, B.x, A.x } |
| `m_chunkBase[1]` | { D.y, C.y, B.y, A.y } |
| `m_chunkBase[2]` | { D.z, C.z, B.z, A.z } |

Use `mIndex` to identify which element within a chunk belongs to a specific object.

### Debugging Tips

1. **OGRE_USE_SIMD=0**: Recompile with this to force C fallback (1 element per ArrayVector3)
2. **mIndex**: Always check this to know which packed element you're looking at
3. **Dummy pointers**: Uninitialized slots point to a dummy node, not NULL (DOD pattern)
4. **Watch syntax**: In debuggers, use `mObjectData.mParents,4` to see all 4 elements

### Memory Manager Types

- **ArrayMemoryManager**: Base SoA memory manager
- **NodeMemoryManager**: Manages SceneNode transforms
- **ObjectMemoryManager**: Manages MovableObject data

These managers handle memory in contiguous chunks for cache-friendly iteration.

## Porting from OGRE-Next 2.2 to 2.3

Key changes when upgrading to 2.3:

### API Changes

1. **Mesh import**: Use `MeshManager::createByImportingV1()` instead of deprecated `Mesh::importV1()` - the new function handles device-lost recovery automatically

2. **Shadow mapping**: `HlmsManager::setShadowMappingUseBackFaces()` was **removed** - use Normal Offset Bias instead via `ShadowTextureDefinition::normalOffsetBias` and `constantBiasScale`

3. **notifyDataIsReady()**: Don't call more than needed - each call must have a preceding `scheduleTransitionTo(Resident)` or `scheduleReupload()`. For `ManualTexture`, OGRE calls it automatically

4. **HlmsMacroblock::mDepthClamp**: New member added - rebuild everything after upgrade to avoid ABI issues

5. **Root constructor**: The documented 2.3 constructor now takes an app name string as the last parameter for driver profile identification; sample-framework code may also use an `AbiCookie` overload, so follow the constructor expected by the framework code you copied

### Unlit Shader Unification

Unlit vertex/pixel shaders were unified into single `.any` files. When upgrading:
- Ensure old `.glsl`/`.hlsl`/`.metal` files from Unlit don't linger
- Verify `Samples/Media/Hlms/Unlit` files match 1:1 with your project
- Custom Unlit implementations may need updates (see Colibri GUI commits for reference)
